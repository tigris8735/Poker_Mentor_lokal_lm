# План тестирования

## 1. Стратегия тестирования

### 1.1. Общий подход
Тестирование Poker Mentor проводится по методологии **многоуровневого тестирования** с акцентом на интеграционное тестирование из-за сложности взаимодействия компонентов.

### 1.2. Уровни тестирования
- **🔧 Модульное тестирование**: Отдельные компоненты и функции
- **🔄 Интеграционное тестирование**: Взаимодействие между модулями  
- **🎯 Системное тестирование**: Полная система в среде, близкой к production
- **👥 Приемочное тестирование**: Соответствие пользовательским требованиям

## 2. Объекты тестирования

### 2.1. Ключевые модули для тестирования

#### **🎮 Игровая система**
- `PokerEngine` - логика покерной механики
- `GameManager` - управление игровыми сессиями
- Игровые обработчики (`/game`, `/fold`, `/call`, `/raise`)

#### **🤖 AI-компоненты**
- `AIService` - управление AI-запросами
- `LLMClient` - взаимодействие с LM Studio API
- `OfflineAIService` - резервная система

#### **💾 Система данных**
- `Database` service - операции с базой данных
- Модели `User` и `HandHistory` - целостность данных

#### **⚡ Основная инфраструктура**
- Инициализация бота (`main.py`)
- Маршрутизация команд
- Обработка ошибок и исключений

## 3. Методы тестирования

### 3.1. Функциональное тестирование

#### **Тест-кейсы игрового процесса**
```python
# Пример тест-кейса
Test Case: "Начало новой игры"
- Действие: Пользователь отправляет /game
- Ожидаемый результат: 
  ✓ Создается новая игровая сессия
  ✓ Раздаются карты игроку и AI
  ✓ Отображается интерфейс с доступными действиями
  ✓ Устанавливаются начальные блайнды (10/20)
```

#### **Тест-кейсы AI-интеграции**
```python
Test Case: "Анализ раздачи при доступном AI"
- Предусловие: LM Studio запущен и доступен
- Действие: Пользователь отправляет /analyze с описанием раздачи
- Ожидаемый результат:
  ✓ AI возвращает профессиональный анализ
  ✓ Ответ содержит конкретные рекомендации
  ✓ Время ответа < 10 секунд
```

### 3.2. Интеграционное тестирование

#### **Сценарии взаимодействия**
1. **Полный игровой цикл**
   ```
   /game → раздача карт → /call → AI ход → /raise → шоудаун
   ```

2. **AI-анализ с переключением режимов**
   ```
   /analyze → проверка AI → (доступен: AI-ответ | недоступен: оффлайн-совет)
   ```

3. **Управление пользовательскими данными**
   ```
   /start → создание/загрузка профиля → игра → сохранение статистики
   ```

### 3.3. Нагрузочное тестирование

#### **Цели нагрузочного тестирования**
- Поддержка 50+ одновременных пользователей
- Стабильность при частых игровых действиях
- Эффективное управление памятью в длительных сессиях

#### **Метрики производительности**
- **Время отклика**: <2 сек для простых команд, <10 сек для AI-анализа
- **Использование памяти**: стабильное без утечек
- **Нагрузка на CPU**: адекватная для локального развертывания

## 4. Критерии успеха тестирования

### 4.1. Критерии прохождения тестов

#### **Функциональные критерии**
- ✅ Все игровые команды выполняются без ошибок
- ✅ AI-анализ возвращает осмысленные ответы
- ✅ Оффлайн-режим активируется при недоступности AI
- ✅ Данные пользователей сохраняются корректно

#### **Производительностные критерии**
- ✅ Время отклика соответствует требованиям
- ✅ Отсутствуют утечки памяти при длительной работе
- ✅ Система стабильна при одновременной работе multiple users

#### **Критерии удобства использования**
- ✅ Интерфейс интуитивно понятен новым пользователям
- ✅ Сообщения об ошибках информативны и полезны
- ✅ Навигация по командам логична и последовательна

### 4.2. Критерии завершения тестирования

- **Прохождение 95%+ тест-кейсов**
- **Отсутствие критических багов** (блокирующих функциональность)
- **Удовлетворительные показатели производительности**
- **Положительная обратная связь от тестовых пользователей**

## 5. Инструменты тестирования

### 5.1. Автоматизированное тестирование
- **pytest** - фреймворк для модульных и интеграционных тестов
- **unittest.mock** - мокирование внешних зависимостей (Telegram API, LM Studio)
- **aioresponses** - мокирование асинхронных HTTP-запросов

### 5.2. Ручное тестирование
- **Тестовые сценарии** для полного покрытия пользовательских путей
- **Чек-листы** для регрессионного тестирования
- **Тестовые пользователи** с различными уровнями опыта

### 5.3. Мониторинг в production
- **Structured logging** для отслеживания ошибок
- **Метрики производительности** времени ответа
- **Статистика использования** команд и функций
